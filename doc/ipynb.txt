*ipynb.txt*  jupyter notebooks in neovim

install                                                        *ipynb*

use lazy.nvim's package spec, including on lazyvim: >lua
  { "WhiteHades/ipynb.nvim", lazy = false, opts = {} }
<
:Lazy sync installs Lua dependencies and runs the notebook installer.
:IpynbInstall runs the same installer to repair or update the runtime.
Both check scripts/prerequisites.sh before helper, parser, or engine setup.
If all required tools are ready, no prerequisite installation runs. Missing
tools open a terminal with an install plan and a confirmation prompt, including
sudo when needed. A successful check continues installation. Headless Neovim
stops with a shell command instead of waiting for input.

The build needs Neovim 0.12+, uv 0.13.1+, Rust/Cargo 1.88+, Git, curl,
tar, pkg-config, a C/C++ compiler, and tree-sitter-cli 0.26.1+. Inline plots need
ImageMagick's magick command and a compatible terminal, such as Kitty or Ghostty.
The engine and parsers build from source; no prebuilt engine is installed.

New helper environments use Python 3.15.0 through uv, separate from project Python.
Existing helper environments are reused. System Python, venv, and ensurepip are
not required. From the plugin checkout: >sh
  uv run --no-project --python 3.15.0 -- scripts/setup.py --venv /path/to/helper/venv
<
To check host tools without installing them, run: >sh
  bash scripts/prerequisites.sh --check
<
Use --install to preview changes and ask before installing. --yes explicitly
accepts the plan without a confirmation prompt; sudo may still need a password.
--no-images skips ImageMagick. Rust is the only execution backend;
the old --python-backend flag is no longer supported.

The helper supports apt, dnf, pacman, and Homebrew. Pacman also upgrades the
system. Missing or old uv and Rust use the supported system facility or an
official upstream installer when packages are unavailable or too old. The Rust
fallback can select Rust 1.88.0 as your default toolchain. User installers do
not edit shell profiles. Put ~/.local/bin and ~/.cargo/bin on PATH before
running uv or restarting Neovim.
Restart after installation or an engine update. :checkhealth ipynb checks setup.

configuration                                              *ipynb-options*

all options are optional. do not set python unless using an existing environment.
>lua
  opts = {
    python = "/path/to/venv/bin/python",
    jupytext = "/path/to/venv/bin/jupytext",
    images = false,
    numpy_legacy_repr = true,
    keymaps = true,
    auto_init = false,
    auto_setup = true,
    output = { preview_lines = 8 },
  }
<
python supplies Jupytext conversion and kernel discovery, independently of
project Python. The Rust process owns execution state and Jupyter transport.
Python notebooks with a generic python3 kernelspec use the nearest project's
.venv, resolved from the notebook path. Without a Python project, the notebook's
directory is the root, even inside an unrelated Git repository. No user kernel
registration is needed.

auto_setup=true is the default. On first execution, uv sets up a missing .venv.
For an existing pyproject.toml, the plugin runs uv sync with --locked when uv.lock
exists. It adds ipykernel with uv add --dev only if ipykernel is missing.
For a standalone notebook, uv init --bare --vcs none --name notebook-env and
uv add --dev ipykernel create pyproject.toml, uv.lock, and .venv in its directory.
An existing .venv with ipykernel stays unchanged.

Setup needs uv and may need network access. Failures report an error without
using global execution packages. Set auto_setup=false to disable automatic
installation and provide a .venv with ipykernel yourself.

kernel overrides automatic selection. Named notebook kernels and non-Python
kernels remain registered-kernel selections. :IpynbInit opens a picker including
project Python and registered/shared kernels. Remote kernels and connection
files remain available. Local kernels start in the notebook's project directory.

Completion and diagnostics use your existing Python language server. Pyright
and basedpyright use the selected local Python, with separate project roots.
kernel_python remains an optional LSP override; it does not select execution.
Do not point python at every project's environment. The plugin does not use or
change g:python3_host_prog, which belongs to other plugins.

numpy_legacy_repr uses numpy's legacy="1.25" setting in new local python kernels.
it changes display, not values or dtypes. external kernels keep their own setup.
previously saved outputs retain their original text until those cells run again.

custom runtimes must provide requirements.txt themselves. the build step checks
them and builds the Rust engine without changing their Python packages.
With build=false, run :IpynbInstall after updates to rebuild the engine.
Other environments can still be registered with ipykernel and chosen explicitly.

without lazy.nvim, install the dependencies listed in lazy.lua with your package
manager, put this plugin on runtimepath, then call require('ipynb').setup(opts).
Install the markdown, markdown_inline and python treesitter parsers and run
:IpynbInstall.

the bundled runtime uses Ipynb commands and its own Lua namespace.
it does not register or replace Molten commands from a separate installation.

saving                                                       *ipynb-saving*

:w converts the editable Markdown and writes cell outputs in one atomic update.
Execution marks changed outputs as unsaved, even when the code stays unchanged.
The persistent Jupytext helper preserves notebook metadata, cell ids, and
attachments. Rust handles JSON output and rejects writes when the file changed
on disk since opening or saving. Reopening imports outputs without starting a
kernel or executing cells by default. A missing or empty .ipynb opens with one
empty code cell. Kernel memory is not stored; save model checkpoints
separately. Exporting outputs also rejects concurrent disk changes. Ambiguous
output-to-cell matches are rejected instead of writing results into the wrong cell.

rust backend                                                *ipynb-rust*

:IpynbInstall builds native/target/release/ipynb-engine with Cargo. The engine
uses Rust edition 2024. Python notebook cells still run in the selected Jupyter
kernel; rewriting the coordinator does not accelerate their Python calculations.
The small Python helper supplies Jupytext conversion and kernel discovery.
requirements.txt lists only Jupytext and ipykernel, which install the required
Jupyter and nbformat libraries. NumPy, Matplotlib, Pillow, pynvim, and jiter are
not helper requirements. Install plotting packages in each notebook project's
environment when its cells need them. Optional Plotly, Kaleido, pnglatex, and
CairoSVG renderers need their own packages in the helper environment.

The Rust engine starts only when a notebook needs it. Lua registers its commands
directly, so :UpdateRemotePlugins is not needed. :checkhealth ipynb checks the
engine and helper. If the engine is missing, notebook operations report an error
and ask you to run :IpynbInstall. Setup and :IpynbInstall still work before the
engine is built. No Python execution fallback is provided.
Set binary="/path/to/ipynb-engine" to use a separately built executable.

Kernels start on first execution by default. auto_init=true starts one on open.
If a kernel exits, saved and unsaved displayed results stay available. Running
the next cell starts a replacement without rerunning earlier cells. :IpynbInfo
shows the selected interpreter, working directory, and selection reason.

The Python execution backend and optional jiter decoder have been removed.
Remove backend="python" from older configurations. backend="rust" is accepted
for compatibility but is unnecessary. IPYNB_DISABLE_RUST no longer has an effect.

keys                                                           *ipynb-keys*

:Ipynb         open the notebook action menu
<localleader>n  open the same menu
<C-CR>         run cell
<S-CR>         run cell and move to the next code cell
<localleader>b  insert code cell below
<localleader>m  insert markdown cell below
<localleader>s  interrupt execution
<localleader>r  run cell or visual selection
<localleader>R  run all cells
<localleader>a  run cell and above
<localleader>o  open and focus output; normal vim motions scroll it
<localleader>O  close output; q and <Esc> also work inside the output window
<localleader>x  open the first image in the terminal viewer
<localleader>i  restart kernel; keep displayed outputs and clear variables

existing keyboard mappings are not replaced. keymaps=false disables notebook keys.

commands                                                    *ipynb-commands*

:IpynbEnterOutput / :IpynbHideOutput  open and focus / close full output
:IpynbImagePopup                     enlarge the current cell's first image
:IpynbOpenInBrowser                  open the current cell's HTML in a browser
:IpynbYankOutput                     copy text output to the unnamed register
:IpynbYankOutput!                    copy text output to the system clipboard
:IpynbInterrupt / :IpynbRestart      interrupt execution / restart the kernel
:IpynbInfo                           show kernel information

images                                                        *ipynb-images*

image.nvim outputs fit their available space, including enlarging small images.
inline images use at most 90% of the content width and 75% of the available
height, preserving aspect ratio. Markdown's percentage caps do not apply to
notebook previews; image.nvim's absolute max_width/max_height limits still do.
output.height and output.width optionally cap the full output window.
Kitty-compatible terminals receive explicit cell dimensions, so Docker/SSH
pixel-size estimates cannot leave a small bitmap inside a large output area.

with :set mouse=a, click an image in normal or insert mode to open just that
image in a centered terminal viewer. :IpynbImagePopup and <localleader>x open the first image in the current
cell. the viewer fits within 85% of the editor, resizes with the terminal, and
closes with q or <Esc>. existing mouse mappings take precedence.
it does not require a desktop image application.
other image providers retain their existing external popup behavior.
